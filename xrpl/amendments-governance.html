Amendments & Governance

How the XRPL changes its rules: who proposes, who votes, the 80% for two weeks rule, and why servers must update.

01

What an amendment is

An amendment is how the XRPL changes its own rules.

Any change to how the XRPL processes transactions is introduced as an amendment. That covers new features, such as a new transaction type, and also bug fixes that change how transactions are processed.

Built into the software

The code for an amendment ships inside a server software release before anyone can vote on it.

Voted on by validators

Validators vote on each amendment. The vote happens on the network itself.

Enabled for everyone

If an amendment passes, its rule applies to every later ledger version, for everyone at once.

02

Who proposes and who votes

Anyone can propose. Only trusted validators decide.

XRPL server software is open source. A change usually starts as a public discussion and an XRP Ledger Standard (XLS) document in the XRPL-Standards repository. Bug fixes don’t need an XLS, but they may still need an amendment.

Only validators vote on amendments, and only votes from trusted validators count. Each server has a UNL (Unique Node List), its list of validators it trusts not to collude. By default, servers use two recommended lists, one published by the XRPL Foundation and one published by Ripple. Each operator can change their server’s list, and can change their own amendment votes at any time.

Reality Check

List publishers don’t validate transactions, but the official docs say they wield significant power in choosing which validators are widely trusted.

03

The 80% for two weeks rule

Support has to be strong and it has to last.

An amendment is enabled only after it holds support from more than 80% of trusted validators for two weeks.

Flag ledgers

Every 256th ledger is a flag ledger, typically about 15 minutes apart. Votes are counted around each one.

Majority reached

When support passes 80%, the network records that the amendment gained a majority and the two-week clock starts.

Majority lost

If support falls to 80% or less, the clock resets. An amendment can gain and lose a majority any number of times.

Real example

The fixAmendmentMajorityCalc amendment fixed a rounding bug that could let an amendment activate with slightly less than 80%, for example 28 of 36 validators (about 77.8%). It was enabled on 2021-04-08. Since then the minimum is never less than 80% of trusted validators.

04

Activation is permanent

Once enabled, there is no off switch.

  • When an amendment passes, the change applies permanently to all later ledger versions.
  • Turning off a passed amendment requires a new amendment, which has to pass the same vote.
  • If an amendment’s code is removed from the software without it ever being enabled, the network treats it as vetoed.
  • Two years after an amendment is enabled on Mainnet, it can be retired under XLS-11: the old pre-amendment code is removed and the new rule becomes part of the core protocol.
05

Amendment-blocked servers

A server that doesn’t understand the new rules stops instead of guessing.

When an amendment is enabled, servers running older software without that amendment’s code no longer understand the network’s rules. Instead of misreading ledger data, they become amendment blocked. A blocked server can’t:

  • Determine whether a ledger is valid.
  • Submit or process transactions.
  • Take part in consensus.
  • Vote on future amendments.

How a server voted doesn’t matter. Every server follows the amendments the network enabled, so being blocked depends only on whether the server has the code. The fix is to upgrade to the newest server software.

Why operators must update

If you don’t run a server yourself, this is the job of whoever runs the server your app or exchange connects to. A server that misses an update can’t confirm or submit transactions until it upgrades.

06

Fixes vs features

Both go through the same vote.

Feature

Adds something new. Example: the AMM amendment added automated market makers to the XRPL. It was enabled on 2024-03-22.

Fix

Corrects behavior. Many fix amendments have names that start with “fix”, such as fixAmendmentMajorityCalc. Bug fixes that change transaction processing still need an amendment.

Replaced

Sometimes a problem is found first. The Batch amendment was removed from the server software in version 3.1.1 because of a bug and replaced by a new amendment, BatchV1_1.

Each validator operator chooses a vote for each amendment. If the operator doesn’t choose, the server uses a default vote set in the software, and that default can change between releases.

07

The Negative UNL is not governance

It keeps the network moving during outages. It doesn’t change any rules.

The Negative UNL is a list of trusted validators that the other validators agree appear to be offline or malfunctioning. Those validators are temporarily ignored when counting whether a new ledger has reached consensus, so the network can keep confirming ledgers during a partial outage.

The official docs say it has no impact on how the network processes transactions or what their outcomes are. It doesn’t vote on rules, and it doesn’t remove anyone from a UNL. The Negative UNL itself was added by the NegativeUNL amendment, enabled on 2021-11-21.

08

Common misconceptions

What people often get wrong about XRPL governance.

“Ripple can flip a switch.” No single server can enable or disable an amendment. It needs more than 80% of trusted validators for two weeks.
“Holding $XRP gives me a vote.” Only validators vote on amendments. Holding $XRP isn’t a vote.
“A passed amendment can be undone easily.” Undoing it takes a new amendment that passes the same vote.
“Updating server software is optional.” A server without the code for an enabled amendment becomes amendment blocked.
“The Negative UNL is a governance vote.” It only helps the network keep confirming ledgers when validators are offline.
“Open for voting means it’s coming.” Many amendments stay below 80% for a long time, and some are never enabled.
09

How to see current votes

Check the official list, not a screenshot.

The Known Amendments page on xrpl.org lists every amendment that is enabled on Mainnet or open for voting, with its current support. Support changes as validators update their votes, so always check the live page.

Read it like this

“Enabled” with a date means the rule is live and permanent. “Open for Voting” with a percentage means validators are still deciding. “Obsolete” means the code was removed.
