서명 요청을 실제 결과까지 따라가세요

지갑을 여는 것, 요청에 서명하는 것, 원장 동작을 완료하는 것은 서로 다른 사건입니다. 화면은 각 단계에서 진실을 말해야 합니다.

먼저 배우고 살펴보세요. 이 페이지에는 지갑 연결, 시드(seed) 입력, 서명, 트랜잭션이 없습니다.

시작하기 전에

프로젝트 정체성과 권한 노트를 가져오세요. 이 레슨에는 지갑이 필요 없습니다. 나중에 연동을 구현한다면 별도의 테스트 환경과 현재 공식 Xaman 문서를 사용하세요.

만들 결과: 올바른 사용자와 의도를 묶고, 불확실함을 설명하며, 필요한 증거 뒤에 결과를 한 번만 부여하는 서명 여정을 설계하세요.

쓰게 될 단어

페이로드
자체 식별자가 있는, 특정 지갑 서명 요청입니다.
콜백 또는 웹훅
무언가 바뀌었을 수 있다고 애플리케이션에 알리는 메시지입니다. 기준이 되는 결과를 가져와 확인하세요.
백엔드
비밀과 기준이 되는 주문 확인이 있어야 할, 애플리케이션의 서버 쪽입니다.
검증된 원장
네트워크 합의로 받아들여진 원장입니다. 제출 응답만으로는 이 최종 증거가 되지 않습니다.
멱등(idempotent)
주문을 두 번 부여하는 것처럼 업무 효과를 반복하지 않고, 여러 번 처리해도 안전한 것입니다.

분명한 요청으로 시작하세요

Xaman 페이로드는 서명 요청입니다. 제품은 먼저 동작, 네트워크, 서명 계정, 정확한 자산, 받는 쪽, 금액 또는 권한을 설명해야 합니다. 로그인은 계정을 식별하는 것이지 지급이 아닙니다. 사용자에게 시드(seed), 비밀 번호, 개인 키를 페이지에 붙여 넣으라고 요청하지 마세요.

사용자에게 실제 선택을 주세요

독립적으로 살펴볼 수 있도록 지갑에 요청을 보여 주세요. 거절, 취소, 만료를 정상적인 결과로 다루세요. 웹사이트로 돌아오거나 QR을 스캔한 것만으로는 아무것도 증명되지 않습니다. 의도한 동작을 올바른 사용자/세션과 요청 식별자에 묶으세요. 다른 요청의 결과를 받아들이지 마세요.

콜백 너머를 확인하세요

콜백(callback)은 백엔드가 페이로드 결과를 가져올 이유이지, 그대로 믿어도 된다는 증거가 아닙니다. resolved/signed 상태, 예상 계정, 의도한 네트워크를 확인하세요. 원장 트랜잭션이라면 트랜잭션 해시를 조회하고 검증, 결과, 의도한 작업을 그대로 확인하세요. 서명된 요청도 원장에서 실패하거나 미해결로 남을 수 있습니다.

지급 사실 확인

지급이라면 받는 쪽, 자산 정체성, 전달된 금액, 필요한 목적지 태그(destination tag)/참조를 저장된 의도와 비교하세요. 부분 지급(partial payment) 때문에 요청 금액만으로 영수증을 만들면 위험합니다. 메타데이터의 delivered_amount를 살펴보세요. 트랜잭션을 한 번만 기록해서 반복 콜백이 두 번째 권리를 주지 않게 하세요. 원장 증거가 알 수 없거나 이용할 수 없으면 대기 상태로 두세요.

가상 예약을 모든 상태로 걸어 보세요

의도한 연습 네트워크에서 Club Treasury로 가는 5 XRP 워크숍 예약의 가상 주문 O-17을 쓰세요. 실제 주소나 지급은 주어지지 않습니다. 주문 정체성, 지갑 요청 정체성, 트랜잭션 해시를 서로 다른 세 필드로 두세요.

  1. 요청이 생기기 전에 저장할 의도를 적으세요. 고객/세션, 예상 동작, 필요할 때의 예상 서명자, 목적지, 네트워크, 자산, 금액, 라우팅 태그, 만료, 주문 참조입니다. 칸에 입력한 지갑 주소는 통제의 증거가 아닙니다.
  2. 회원이 봐야 할 확인 문구를 쓰세요. 무슨 일이 일어나는지, 누구에게, 얼마인지, 무엇을 승인하지 않는지입니다. 계정 SignIn과 Payment를 나누세요. 신원을 확인하려고 관계없는 트랜잭션에 서명하라고 하지 마세요.
  3. 요청됨에서 거절됨, 만료됨, 또는 서명됨으로 가는 그림을 그리세요. 서명 뒤에 확인 대기를 넣고, 그다음 검증된 완료 또는 확인된 실패를 넣으세요. 브라우저로 돌아오기, QR 스캔, 클릭은 서명된 결과가 아닙니다. 서명된 결과가 자동으로 성공한 지급은 아닙니다.
  4. 백엔드에서 요청 식별자를 O-17에 묶으세요. 알림이 오면 페이로드 결과를 가져와 그 기록과 비교하세요. 예상 서명자와 네트워크를 확인하세요. SignIn은 묶인 증명과 세션을 확인합니다. 받았다고 가장할 지급 트랜잭션은 없습니다.
  5. Payment라면 의도한 네트워크에서 트랜잭션과 메타데이터를 가져오세요. 검증된 성공, 올바른 트랜잭션 유형, 받는 쪽, 자산 정체성, 실제 전달된 금액, 필요한 라우팅 필드를 요구하세요. 스크린샷, 브라우저가 준 성공 표시, 요청 금액만으로는 부족합니다.
  6. 완료와 그 고유한 트랜잭션 참조를 하나의 업무 동작으로 지속되게 저장하세요. 같은 알림을 세 번 전달해도 예약은 하나여야 합니다. 확인과 권리 업데이트 사이에 서버가 멈추면, 복구는 같은 주문을 끝내야 하며 두 번째 지급 요청을 만들면 안 됩니다.
풀어 본 결정

5 XRP 주문에서 요청 금액은 5인데 검증된 전달 금액은 1뿐이라고 상상하세요. 주문은 전액 결제된 것이 아닙니다. 전달 금액을 알 수 없으면 추측하지 말고 확인을 미해결로 두세요. 증거는 맞지만 콜백이 반복되면, 좌석을 또 주지 말고 기존 영수증을 보여 주세요.

선택: 작업지를 공개 기록에 연결하기

읽기 전용 탐색기에서 올바른 네트워크의 공개 Payment 해시를 살펴보세요. 검증 상태, 트랜잭션 결과, 보낸 쪽, 목적지, 자산, 메타데이터의 전달 금액을 찾으세요. 요청 금액과 실제 전달을 구분하세요. 공개 해시는 영수증을 읽는 법을 가르쳐 줄 수 있습니다. 자신의 가상 주문이 결제되었다는 증거로 재사용하면 안 됩니다.

공식 XRPL 탐색기 목록 · 네트워크 아멘드먼트 참고. 공개 기록을 읽기만 하는 데는 지갑이 필요 없습니다. 이 연습에 개인 정보나 비공개 정보를 입력하지 마세요.

흔한 문제와 확인할 것

회원이 서명했지만 페이지가 시간 초과되었습니다

지급 확인 중임을 보여 주고 같은 요청/트랜잭션을 복구하세요. 두 번째 지급을 자동으로 권하지 마세요. 사용자가 대기 주문으로 어떻게 돌아오는지 설명하세요.

다른 지갑이 요청에 응답했습니다

의도한 정체성과 정책과 비교하세요. 계정 통제가 필요한데 서명자가 다르면 거절하세요. 주문 소유자를 조용히 다시 이름 붙이지 마세요.

Testnet에서는 성공했지만 실제 주문은 잠긴 채입니다

의도한 네트워크와 관찰된 네트워크를 확인하세요. 테스트 잔액과 트랜잭션으로 Mainnet 주문을 결제할 수 없습니다. 테스트가 성공한 것처럼 보이게 네트워크 확인을 느슨하게 하지 마세요.

넘어가기 전에 보관할 것

상태 그림, O-17 의도 작업지, 확인 필드 목록, 중복/재시작 시나리오를 보관하세요. 이것은 설계 산출물이지, 운영에 바로 쓸 인증이나 지급 코드가 아닙니다.

풀어 본 예시를 보지 말고 답을 설명한 다음 비교하세요. 추측했다면 해당 부분을 다시 보세요. 체크박스와 퀴즈 피드백은 이 페이지에만 남습니다. 프로젝트 노트는 직접 보관하세요.

판단 비교하기

결제됨도 아니고 다시 내라는 요청도 아닌, 복구할 수 있는 확인 대기를 보여 주세요. 같은 묶인 트랜잭션을 다시 확인하세요. 검증된 성공 지급이 의도한 받는 쪽, 자산, 전달 금액과 일치한 뒤에만 주문을 완료하세요. 서명되었더라도 맞지 않는 요청은 거절하세요.
